# 웹앱 카드 이미지 지침

이 문서는 루트 교과 카드 또는 교과 내부 웹앱 카드의 이미지를 새로 만들거나 교체할 때 읽는다. 카드 이미지는 장식이 아니라 실제 웹앱의 핵심 조작과 수학적 변화를 미리 보여주는 시각적 안내여야 한다.

파일명, 상대경로, 목록 페이지 구조는 `repo-structure.md`, 완료 전 공통 검증은 `verification.md`를 함께 따른다. 특정 교과나 카드 묶음의 일회성 작업지시서를 작성할 때는 `task-spec.md`와 `card-image-task-spec-template.md`도 함께 읽는다. 공통 규칙을 일회성 문서에 반복해서 복사하지 말고, 템플릿에 실제 앱 조사 결과와 해당 작업의 결정만 채운다.

## 핵심 원칙

- 카드 제목, 소개 문구, 폴더 이름만 보고 이미지를 설계하지 않는다.
- 카드의 실제 `href` 대상 웹앱을 열고 구조와 동작을 확인한 뒤 시안을 만든다.
- 최종 결과만이 아니라 학생의 조작에 따라 일어나는 변화 과정이 드러나게 한다.
- 장식보다 실제 수학 구조와 학습 장면을 우선한다.
- 앱을 실행하거나 핵심 내용을 이해할 수 없으면 제목으로 추측해 이미지를 만들지 않고 확인하지 못한 이유를 보고한다.
- 사용자가 카드별 시안을 명시적으로 승인하기 전에는 이미지 생성, 파일 저장, HTML/CSS 적용, 커밋, 푸시를 하지 않는다.

## 작업 단계와 승인 경계

카드 이미지 작업은 다음 순서로 진행한다.

1. 대상 목록 페이지와 카드의 실제 링크를 확인한다.
2. 실제 웹앱의 파일 구조와 동작을 조사한다.
3. 카드별 대표 장면과 스타일 참조 이미지를 정한다.
4. 카드별 시안을 사용자에게 제안하고 작업을 멈춘다.
5. 사용자가 시안을 승인하면 이미지를 생성하고 품질을 검토한다.
6. 승인된 이미지만 최적화하여 목록 페이지에 적용한다.
7. 링크, 접근성, 반응형 배치, 콘솔 오류와 파일 용량을 검증한다.

사용자가 처음부터 이미지 제작을 요청했더라도 아직 카드별 시안에 대한 승인이 없다면 4단계에서 멈춘다. 시안 승인과 실제 제작 요청이 함께 명확히 주어진 경우에만 다음 단계로 진행한다.

## 제작 전 실제 웹앱 조사

### 1. 링크와 파일 구조 확인

- 목록 페이지에서 카드의 실제 `href`를 찾는다.
- 링크 대상 HTML을 읽고 연결된 JavaScript, CSS, JSON, 이미지와 기타 정적 리소스를 확인한다.
- Canvas, SVG, WebGL 또는 three.js 장면이 있으면 렌더링 코드와 상태 갱신 방식을 확인한다.
- 웹앱 제목과 설명이 실제 기능과 일치하는지도 확인한다.

### 2. 브라우저 실행과 대표 조작

- 웹앱을 로컬 브라우저에서 직접 실행한다.
- 주요 버튼, 슬라이더, 입력값과 단계 전환을 실제로 조작한다.
- 초기 상태, 변화 중간 상태, 대표 결과 상태를 관찰한다.
- 자동 실행이나 애니메이션이 핵심이면 변화 경로와 누적 과정을 관찰한다.
- 3D 장면이면 대표 시점과 카메라 조작에 따른 공간 관계를 확인한다.
- 화면 일부만 보고 판단하지 말고 학생이 수업에서 밟게 될 대표 흐름을 끝까지 확인한다.

### 3. 카드별 조사 기록

각 카드에 대해 다음을 짧게 정리한다.

```md
카드:
실제 링크:
확인한 파일과 장면:
학습 목표:
핵심 조작:
조작에 따라 즉시 변하는 요소:
학생이 관찰해야 할 변화:
대표적인 수학 장면:
다른 카드와 구분되는 특징:
이미지에 넣으면 오해를 일으킬 요소:
```

## 이미지 제작 전 시안 제안

조사를 마친 뒤 각 카드의 시안을 다음 형식으로 제안한다.

```md
카드:
실제 확인한 웹앱:
핵심 조작:
핵심 변화:
이미지에 담을 대표 장면:
권장 구도:
기존 스타일 참조 이미지:
참조 이미지에서 계승할 요소:
피해야 할 표현:
예상 파일 경로:
```

같은 목록에 여러 카드가 있으면 카드별 시안과 함께 전체 세트의 통일 방식도 제안한다. 색감과 질감은 통일하되 핵심 도형, 시점과 변화 경로가 반복되지 않게 한다.

## 공통 스타일

현재 카드 이미지의 공통 스타일 이름은 다음과 같이 정의한다.

> **Soft Scientific Editorial Illustration**
> 밝은 과학 교과서형 편집 일러스트

### 전체 인상

- 차분하고 친근한 고등학교 과학·수학 교과서 분위기를 유지한다.
- 기술적이지만 차갑거나 사이버펑크처럼 보이지 않게 한다.
- 하나의 핵심 수학 장면과 넉넉한 여백을 사용한다.
- 장식이나 캐릭터보다 그래프, 도형, 데이터, 이동 경로와 변화 과정이 먼저 보이게 한다.
- 같은 목록의 이미지는 색감, 선 굵기, 여백과 시각적 밀도가 한 세트처럼 보이게 한다.

### 색상 역할

- 배경: 흰색과 아주 옅은 회청색
- 주요 수학 선: 짙은 남색과 코발트블루
- 변화, 이동, 선택: 청록색과 민트색
- 보조 면과 공간: 옅은 하늘색, 회청색과 라벤더색
- 게임이나 특별한 상태의 강조: 노랑, 주황, 산호색을 제한적으로 사용

색상값을 기계적으로 같게 만드는 것보다 색상의 역할을 일관되게 유지한다. 한 이미지 안에서 강조색을 지나치게 많이 사용하지 않는다.

### 선, 면과 질감

- 수학 도식, 그래프와 윤곽선은 또렷한 벡터 스타일로 표현한다.
- 배경과 넓은 색면에는 매우 옅은 수채화 번짐과 종이 질감을 사용한다.
- 반투명 색면을 제한적으로 겹쳐 공간과 영역을 나타낸다.
- 그림자는 점이나 입체 요소의 구분에 필요한 만큼만 부드럽게 사용한다.
- 3D 곡면은 구조가 읽히는 격자나 등고선을 사용할 수 있지만 제품 렌더링처럼 광택을 내지 않는다.
- 질감이 수학 선과 이동 경로의 가독성을 방해하지 않게 한다.

### 구도

- 기본 화면 비율은 `16:9`이다.
- 하나의 대표 장면을 중심으로 구성하고 중요한 요소 주변에 충분한 안전 여백을 둔다.
- 두 개념을 함께 보여줘야 할 때만 좌우 비교 구도를 사용한다.
- 변화는 점의 연속, 이동 경로, 화살표, 색면 변화 또는 전후 비교로 나타낸다.
- 배경의 물결과 색면은 핵심 수학 도형보다 약하게 표현한다.
- 카드의 `object-fit: cover` 적용 가능성을 고려해 중요한 수학 요소를 가장자리에 붙이지 않는다.

## 기존 이미지 참조

생성 도구가 참조 이미지 입력을 지원하면 내용이 가장 가까운 기존 이미지 1~2장을 스타일 참조로 사용한다. 내용과 구도를 복제하지 않고 색감, 질감, 선 표현, 여백과 시각적 밀도만 계승한다. 서로 다른 유형의 이미지를 모두 한꺼번에 참조하지 않는다.

현재 사용할 수 있는 대표 참조는 다음과 같다.

- 데이터와 분포: `assets/subject-cards/probability-statistics.jpg`
- 2차원 그래프와 넓이: `assets/subject-cards/calculus.jpg`
- 공간도형과 벡터: `assets/subject-cards/geometry.jpg`
- 인공지능수학의 전체 색감: `assets/subject-cards/artificial-intelligence-math.jpg`
- 이동과 수렴 과정: `artificial-intelligence-math/card-images/gradient-descent.jpg`
- 3차원 손실곡면: `artificial-intelligence-math/card-images/linear-intercept-gradient-descent.jpg`
- 지형과 국소 탐색: `artificial-intelligence-math/card-images/local-search-descent.jpg`
- 등고선과 단계형 게임: `artificial-intelligence-math/card-images/contour-search-game.jpg`

새 이미지와 수학 표현 방식이 가장 가까운 참조만 고른다. 기존 참조 파일이 이동하거나 교체되었다면 실제 존재 여부와 현재 스타일을 다시 확인한다.

## 수학 표현 원칙

- 실제 앱에서 사용하는 함수, 곡선, 그래프, 좌표 관계와 이동 경로를 반영한다.
- 최종 결과뿐 아니라 조작과 변화 과정이 드러나게 한다.
- 점의 위치, 크기, 이동 경로, 화살표와 선 모양을 함께 사용해 색상만으로 상태를 구분하지 않는다.
- 실제 앱에 없는 수식, 그래프, 좌표축과 데이터 점을 장식으로 추가하지 않는다.
- 함수 모양, 극값, 회귀선, 확률분포, 벡터 방향과 공간 관계를 수학적으로 틀리게 표현하지 않는다.
- 이미지의 단순화를 위해 세부 눈금과 라벨을 생략할 수 있지만 핵심 수학 관계를 바꾸면 안 된다.
- 여러 상태를 한 장에 합칠 때 서로 다른 시점의 값이 하나의 상태처럼 오해되지 않게 이동 경로나 영역을 분명히 구분한다.

## 피해야 할 스타일과 소재

- 검은 배경과 네온 중심의 사이버펑크 표현
- 일반적인 AI 로봇, 인공지능 뇌와 회로판
- 사람이나 캐릭터가 중심인 만화 스타일
- 사진처럼 사실적인 교실, 사물 또는 풍경
- 광택이 강한 제품 렌더링형 3D
- 과도한 그라데이션, 강한 그림자와 높은 채도
- 이미지 안의 제목, 설명, 숫자, 라벨, 로고와 워터마크
- 의미 없는 수식, 그래프, 좌표축과 데이터 점
- 실제 UI를 그대로 축소한 스크린숏
- 핵심 수학 구조를 가리는 장식과 지나치게 복잡한 배경

문자나 수식이 학습 장면을 구분하는 데 꼭 필요하다면 실제 앱의 정확한 표기만 최소한으로 사용하고 시안 단계에서 그 이유를 밝힌다.

## 파일 규격과 저장 위치

### 권장 규격

- 비율: `16:9`
- 기본 크기: `960×540`
- 일반적인 일러스트 형식: JPEG
- JPEG 권장 품질: 85~90
- 목표 용량: 파일 하나당 150KB 이하
- 최대 권장 용량: 파일 하나당 250KB
- 투명 배경이나 선 중심 도식: 필요할 때 PNG 또는 SVG 검토
- 파일명: 영어 소문자, 숫자, 하이픈만 사용

목표 용량을 맞추기 위해 수학 선이 흐려지거나 압축 흔적이 두드러지면 품질을 우선하고 최종 용량과 이유를 보고한다.

### 저장 위치

- 루트 교과 카드: `assets/subject-cards/<subject-name>.jpg`
- 교과 내부 웹앱 카드: `<subject-folder>/card-images/<app-slug>.jpg`

카드 이미지는 개별 웹앱 폴더가 아니라 해당 목록 페이지를 소유하는 폴더에서 관리한다. 실제 저장 형식이 PNG 또는 SVG이면 확장자와 HTML 경로도 함께 맞춘다.

## HTML과 접근성

- 이미지에 실제 픽셀 크기와 맞는 `width`와 `height` 속성을 명시해 레이아웃 이동을 줄인다.
- 첫 화면에서 우선 보여야 하는 첫 카드 이미지에는 필요할 때 `fetchpriority="high"`를 사용한다.
- 첫 우선 이미지 외에는 `loading="lazy"`와 `decoding="async"`를 사용한다.
- 이미지가 카드 제목과 설명의 의미만 시각적으로 반복하는 장식이면 `alt=""`를 사용한다.
- 이미지가 카드 제목과 설명만으로 알 수 없는 정보를 전달하면 짧고 정확한 대체 텍스트를 제공한다.
- 기존 `.subject-card-image`, `.subject-card-body`와 공통 카드 스타일을 우선 재사용한다.
- 이미지 추가만을 위해 페이지마다 비슷한 CSS를 새로 만들지 않는다.
- 중요한 수학 요소가 `object-fit: cover`로 잘리지 않는지 실제 카드 크기에서 확인한다.

## 공통 이미지 생성 프롬프트 골격

다음 골격은 실제 웹앱 조사를 마치고 대괄호 항목을 구체적인 조사 결과로 교체한 뒤에만 사용할 수 있다. 앱을 실행하지 않았거나 대괄호가 남아 있으면 이 프롬프트를 실행하지 않는다.

```text
16:9의 밝은 과학 교과서형 편집 일러스트.

[실제 웹앱에서 확인한 핵심 수학 장면]을 표현한다.
[학생의 핵심 조작]에 따라 [즉시 변하는 요소]가 변화하는 과정을
[점의 연속, 이동 경로, 화살표, 색면 변화 또는 전후 비교 중 실제 앱에 맞는 방식]으로 보여준다.

흰색과 아주 옅은 회청색의 종이 질감 배경,
깨끗한 짙은 남색·코발트블루 수학 선,
변화와 이동을 나타내는 청록색·민트색 강조,
옅은 하늘색과 라벤더색의 반투명 보조 면을 사용한다.

수학 도식은 정확하고 또렷한 벡터 스타일로 표현하고,
배경과 넓은 색면에는 매우 부드러운 수채화 질감을 사용한다.
하나의 핵심 장면과 넉넉한 여백을 유지한다.
```

## 검증 기준

이미지 생성과 적용을 승인받아 실제 작업한 뒤 다음을 확인한다.

- 이미지가 실제 앱의 핵심 조작과 변화를 반영하는가
- 제목만 보고 만든 일반적인 이미지가 아닌가
- 함수, 그래프, 극값, 회귀선, 분포, 벡터와 공간 관계에 수학적 오류가 없는가
- 기존 이미지와 같은 자료실에서 만든 것처럼 보이는가
- 같은 페이지의 이미지들이 통일되어 있으면서 서로 충분히 구분되는가
- 이미지 URL과 GitHub Pages 상대경로가 정상인가
- 깨진 이미지와 브라우저 콘솔 오류가 없는가
- 중요한 요소가 카드 비율과 `object-fit` 때문에 잘리지 않는가
- iPad A16 가로 `1180×820` CSS px에서 카드 배치가 안정적인가
- iPad A16 세로 `820×1180` CSS px에서 이미지, 제목과 설명이 겹치거나 잘리지 않는가
- 모바일 화면에서 가로 넘침이 없는가
- 이미지 파일 형식, 픽셀 크기와 용량이 권장 범위 안에 있는가
- 장식 이미지와 정보 이미지의 `alt` 처리가 적절한가
