# 카메라·동작 인식 웹앱 제작 기준

카메라로 손, 몸, 얼굴, 물체의 움직임을 인식하는 웹앱을 만들 때 읽는다. 인식 라이브러리는 MediaPipe Tasks for Web(`@mediapipe/tasks-vision`)을 기본으로 본다.

`webapp.md`와 `verification.md`를 대체하지 않는다. 학습 목표, 화면 배치, iPad A16 검증 기준은 그대로 따르고, 여기서는 카메라 인식 앱에서만 문제가 되는 부분을 다룬다.

---

## 0. 만들기 전에 판단할 것

카메라 인식은 무겁고, 권한이 필요하고, 실패할 여지가 많다. 먼저 이 질문에 답한다.

- 슬라이더, 드래그, 버튼으로 같은 학습 목표를 달성할 수 있는가? 가능하면 그렇게 만든다.
- 카메라가 없으면 성립하지 않는 활동인가? 몸의 각도를 실제로 재기, 움직임을 데이터로 모아 분포를 만들기, 몸을 움직이는 경험 자체가 목적인 활동은 카메라가 값을 낸다.
- 반대로 도형 회전, 값 입력, 정밀한 위치 지정은 카메라가 슬라이더보다 나쁘다. 정확도가 떨어지고 학생의 관심이 "어떻게 손을 흔들까"로 옮겨간다.

**성능은 설계보다 먼저 확인한다.** 쓸 모델을 정해 최소 페이지로 로딩 시간과 추론 fps를 먼저 측정한다. 프레임이 나오지 않으면 판정을 관대하게 만들어도 앱이 성립하지 않는다. 이때는 `learning-agent-roles.md`의 판정 체계에 따라 `재설계` 또는 `제작 보류`로 남기고, 구현을 진행하지 않는다.

학생을 대상으로 카메라를 사용하기 전에 학교나 교육청의 개인정보 방침을 확인한다. 아래 §4의 기술적 기준을 지키는 것과는 별개의 문제다.

---

## 1. 무거운 파일은 저장소에 두고 나눠서 받는다

MediaPipe는 JS 라이브러리, WASM 바이너리, 모델(`.task`) 세 종류가 필요하다. 모델 하나가 수 MB 규모이고, 손과 전신을 함께 쓰면 기기당 십수 MB가 된다. 정확한 크기는 파일을 받을 때 확인해 `assets/vendor/`의 `README.md`에 적는다. 학급 전체가 각자 기기로 동시에 받는 상황을 기준으로 설계한다.

- 파일은 `assets/vendor/` 아래에 두고 상대경로로 불러 오프라인에서도 동작하게 한다. `three.js`를 vendoring한 방식과 같다. 추가한 파일 목록과 갱신 방법은 해당 폴더의 `README.md`에 남긴다.
- **모델을 처음에 전부 로드하지 않는다.** 실제로 쓰는 순간에 받는다. 손 인식으로 시작하는 앱이면 손 모델만 먼저 받고, 전신 인식이 필요한 화면에 들어갈 때 전신 모델을 추가로 받는다.
- **로딩 중에는 진행 상태를 보여준다.** 빈 화면으로 기다리게 하면 학생은 앱이 고장난 것으로 판단한다. 무엇을 받고 있는지, 몇 초 정도 걸리는지 문구로 알린다.
- MediaPipe Tasks for Web은 `SharedArrayBuffer` 없이도 동작한다. 다만 GitHub Pages는 COOP/COEP 헤더를 설정할 방법이 없어 **멀티스레드로 성능을 끌어올릴 수단이 아예 없다.** 그러므로 성능은 단일 스레드 기준으로 미리 측정하고 그 안에서 설계한다.
- 프레임이 부족하면 정확도가 낮은 대신 가벼운 모델을 쓰거나, 매 프레임이 아니라 2~3프레임마다 추론한다. 화면 그리기와 추론 주기를 분리한다.

`npm install`이나 빌드 과정은 추가하지 않는다. CDN에서 시험한 뒤, 쓸 파일이 확정되면 vendoring한다.

> 현재 저장소에 MediaPipe 파일은 아직 없다. 처음 쓰는 앱을 만들 때 vendoring부터 하고, 위 기준대로 `assets/vendor/` 아래에 배치한다.

## 2. 인식 결과는 흔들린다는 것을 전제로 판정한다

랜드마크 좌표는 프레임마다 미세하게 떨리고, 빠르게 움직이면 몇 프레임씩 놓친다. 이 흔들림을 그대로 판정에 연결하면 앱이 못 쓰게 된다.

**판정 방식은 활동에 따라 다르다. 두 가지를 구분해서 설계한다.**

### 자세를 맞추는 판정

양손 들기, T자 만들기, 손가락 개수, 손 모양처럼 **정지 상태를 맞히는** 활동이다.

- 한 프레임으로 판정하지 않는다. 조건을 만족하는 상태가 0.3~0.5초 이어질 때 통과로 처리한다. 프레임 하나로 판정하면 우연히 통과하고 억울하게 실패한다.
- 유지해야 하는 시간이 있으면 진행 표시(게이지, 카운트)를 보여준다. 언제 통과하는지 모르는 상태로 기다리게 하지 않는다.

### 움직이는 대상을 맞히는 판정

날아다니는 대상을 손으로 치기, 지나가는 목표를 잡기처럼 **순간적인 접촉**을 판정하는 활동이다.

- **여기에 유지 시간을 요구하면 안 된다.** 손을 대상에 0.4초 붙이고 있으라고 하면 원래 의도한 "빠르게 낚아채는" 동작이 사라진다.
- 대신 판정 범위를 넉넉하게 잡는다. 화면에 보이는 대상보다 큰 판정 반경을 쓴다.
- 손이 빠르게 지나가면 프레임 사이를 건너뛰어 접촉이 누락된다. 이전 프레임과 현재 프레임의 손 위치를 이은 선분이 대상에 닿았는지로 판정하면 놓치지 않는다.
- 실패했을 때 곧바로 다시 시도할 수 있게 한다. 실패마다 대기 시간을 두지 않는다.

**놓친 판정과 우연한 통과 중 무엇이 덜 나쁜지 정하고 그쪽으로 기울인다.** 아이스브레이킹이나 게임은 관대한 쪽이 낫다. 몸의 각도를 재는 측정 활동은 반대로 엄격해야 하므로, 값이 안정될 때까지 판정을 보류한다.

### 두 방식에 공통으로 적용할 것

- **화면에 보여줄 값과 판정에 쓸 값을 분리한다.** 표시용 수치는 최근 몇 프레임의 평균으로 부드럽게 만든다. 소수점이 계속 튀는 숫자는 학생이 읽을 수 없다. 다만 평균을 내면 값이 늦게 따라오므로, 빠른 동작을 판정할 때는 평균이 아닌 원본 좌표를 쓴다.
- **판정 임계값을 코드 상단 상수로 모아 둔다.** 유지 시간, 판정 반경, 자동 통과 시간은 교실에서 조정하게 될 값이다. 코드 곳곳에 흩어 두면 수업 직전에 손볼 수 없다.
- **막혔을 때 빠져나갈 길을 반드시 만든다.** 조명, 카메라 각도, 옷 색깔, 앉은 자세 때문에 특정 학생이 계속 실패하는 일이 실제로 생긴다. 시간이 지나면 자동으로 넘어가거나 건너뛰기 버튼을 제공한다. 이 장치가 없으면 그 학생에게 수업이 멈춘다.
- **카메라를 쓸 수 없는 학생을 위한 대체 경로를 둔다.** 기기에 카메라가 없거나 권한이 거부된 경우, 마우스·터치·키보드로도 활동을 이어갈 수 있게 한다.
- 인식 대상이 화면에 충분히 들어오지 않으면 판정하지 말고 안내를 띄운다. 잘못된 값으로 판정하는 것보다 낫다.
- 전신 인식은 카메라에서 한두 걸음 물러나야 상반신과 팔이 들어온다. **책상에 앉은 iPad로는 전신이 잡히지 않는다.** 상반신 랜드마크만으로 판정할 수 있게 설계하거나, 기기를 세우고 물러서라는 안내를 넣는다. 필요한 실제 거리는 기기와 렌즈 화각에 따라 다르므로 검증에서 확인한다.

## 3. 지금 무엇을 인식하고 있는지 항상 보여준다

학생은 앱의 내부 상태를 볼 수 없다. 인식이 안 되는 것과 앱이 고장난 것을 구별할 방법을 주어야 한다.

- 인식된 랜드마크를 점과 선으로 겹쳐 그린다. 학생이 스스로 손 위치나 자세를 고칠 수 있게 된다.
- 인식 상태를 문구로도 알린다. `카메라 준비 중`, `손이 보이지 않습니다`, `인식 중`, `자세를 유지하세요`처럼 지금 무엇이 필요한지 알려준다. 색 변화만으로 구분하지 않는다.
- **화면은 좌우를 반전해 거울처럼 보여준다.** 반전하지 않으면 학생이 오른쪽으로 손을 움직였을 때 화면에서는 왼쪽으로 가서 조작이 어긋난다. 카메라 영상과 랜드마크 오버레이에 같은 반전을 적용해 둘이 어긋나지 않게 한다.
- 다만 MediaPipe가 알려주는 왼손·오른손 구분은 **촬영된 사람 기준**이다. 화면을 반전해 놓고 `왼손을 드세요`라고 안내하면 학생이 든 손과 라이브러리가 판단한 손이 반대가 될 수 있다. 좌우를 지시하는 활동에서는 반드시 실제 사람으로 확인한다.

## 4. 카메라 권한과 개인정보

- **카메라가 시작되면 영상을 화면에 표시하는 것을 기본값으로 한다.** 학생이 자기 위치와 인식 범위를 바로 확인할 수 있어야 동작 인식 오류를 스스로 고칠 수 있다. 랜드마크 오버레이도 영상 위에 함께 표시한다.
- 영상은 사용자가 언제든 숨길 수 있게 한다. 얼굴과 몸이 화면에 보이는 것이 민감한 수업에서는 교사가 즉시 끌 수 있는 명확한 토글을 제공하고, 숨겨도 동작 인식과 활동은 계속되게 한다.
- 영상이 기기 밖으로 나가지 않는다는 문구를 화면에 표시한다.
- `getUserMedia`는 시작 버튼처럼 학생이 직접 누른 동작 이후에 호출한다. 페이지를 열자마자 권한을 요구하지 않는다.
- 전면 카메라를 쓰도록 `facingMode: "user"`를 지정한다. 카메라가 여러 개인 기기에서 의도한 카메라가 선택되는지 확인한다.
- 권한이 거부되었을 때의 화면을 만든다. 무엇을 거부했고 어떻게 되돌리는지, 카메라 없이 무엇을 할 수 있는지 알린다.
- 촬영한 이미지나 영상을 파일로 저장하거나 어딘가로 전송하는 기능은 넣지 않는다.

## 5. 자원 정리

카메라와 추론 루프는 상태가 꼬이기 쉽다.

- 시작 버튼을 여러 번 눌러도 스트림과 추론 루프가 중복되지 않게 한다.
- 정지·초기화할 때 `requestAnimationFrame` 핸들을 해제하고, 카메라 트랙을 `track.stop()`으로 끈다. 카메라 표시등이 계속 켜져 있으면 학생이 불안해한다.
- 페이지를 벗어나거나 탭이 가려질 때(`visibilitychange`) 추론을 멈춘다. iPad에서 발열과 배터리 소모가 크다.

## 6. 완료 전 추가 점검

`verification.md` 항목에 다음을 더한다.

- 구현 전에 로딩 시간과 단일 스레드 fps를 측정하고 그 결과를 남겼는가?
- 모델과 WASM을 `assets/vendor/`의 실제 파일에서 상대경로로 불러오는가?
- 처음 화면에서 필요하지 않은 모델까지 미리 받고 있지 않은가?
- 로딩 중 진행 표시가 보이는가?
- 자세 판정에 유지 시간이 적용되어 한 프레임으로 통과되지 않는가?
- 순간 접촉 판정에 불필요한 유지 시간을 요구하고 있지 않은가? 빠르게 지나가는 동작을 놓치지 않는가?
- 화면에 표시되는 수치가 튀지 않고 읽을 수 있는가? 빠른 동작 판정에 늦게 따라오는 평균값을 쓰고 있지 않은가?
- 판정 임계값이 코드 상단 상수로 모여 있는가?
- 계속 실패할 때 건너뛰거나 자동으로 넘어갈 수 있는가?
- 카메라 권한을 거부해도 활동을 이어갈 수 있는가?
- 랜드마크 오버레이와 인식 상태 문구가 보이는가?
- 화면이 거울처럼 좌우 반전되어 있고, 영상과 오버레이의 반전이 일치하는가?
- 좌우를 지시하는 활동이라면 실제 사람으로 왼손·오른손이 맞는지 확인했는가?
- 카메라 시작 후 영상 표시가 기본값이고, 영상 숨기기 토글과 로컬 처리 안내 문구가 있는가?
- 시작을 여러 번 눌러도 스트림과 추론 루프가 중복되지 않는가?
- 정지·초기화 후 카메라 표시등이 꺼지는가?
- iPad A16 가로·세로 화면에서 카메라 화면, 조작, 결과가 겹치거나 잘리지 않는가?
